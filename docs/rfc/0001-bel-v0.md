# RFC 0001 — bel v0

|              |                                                                  |
| ------------ | ---------------------------------------------------------------- |
| Status       | Accepted                                                         |
| Supersedes   | `bel言語仕様v0.md` (Japanese draft, deleted)                     |
| Scope        | bel v0: beliefs, flows, guards, tests, compilation to TypeScript |
| Out of scope | `route` / HTTP backends (see "Future work", RFC 0002)            |

## 1. Summary

bel is a guard-driven language in which the condition of a branch is a natural
language statement. A condition is not a boolean expression; it is a **belief**
— a probability produced by a model (TypeSafe Jev). bel compiles to plain
TypeScript, so type checking, editors and the existing ecosystem stay on `tsc`.

```
flow support(t: Ticket): Action
  "the user is angry" @ 0.7 -> escalate(t)
  "the user asks for a refund" -> refund(t)
  _ -> reply("could you tell me more?")
```

The compiler collects every belief a flow needs and asks for all of them in a
single batched evaluation at flow entry. Branching is then ordinary `if`
statements over already-resolved probabilities.

## 2. Motivation

Conditional business logic written against an LLM today is one of two things:
a giant prompt whose output is parsed and `switch`ed on, or a pile of
`if (await classify(x) === "...")` calls scattered through the code. In both,
the questions being asked are not statically visible, thresholds and
confidence handling are ad hoc, and tests have no way to pin decisions.

bel makes three things structural instead of conventional:

1. **Where the model is consulted** is statically enumerable. Beliefs are born
   only in guard conditions and in flow-level `let` bindings. Nothing inside an
   action can create one.
2. **Thresholds and confidence are on the surface.** `@ n` is the only way to
   threshold a belief, and confidence is a first-class value with a defined
   formula.
3. **Deterministic tests are part of the language.** Mock tables, recorded
   model responses and confidence floors are syntax, not a testing library.

## 3. Design principles

1. **Belief layer and action layer are separate.** Every branching condition is
   a belief (a probability). Everything with a side effect is an action (plain
   TypeScript).
2. **Exactly one semantic addition:** a string literal in a condition position
   is evaluated as a belief. Apart from that, bel does not change TypeScript
   semantics.
3. **Do not hide ambiguity.** A belief is a real number in 0–1; thresholds and
   confidence appear on the surface of the language.
4. **Testing is built in.** Swapping the model out (mock, cassette, confidence
   floor) is a grammar-level feature.
5. **Known exception to principle 1.** Inside an action island, a comparison
   against a bound belief/score/choice compiles to an ordinary TypeScript
   comparison (see §8.5). It is a deterministic branch on a number, not a
   belief guard: no threshold, no confidence floor, no trace entry.

## 4. Terminology

| Term          | Meaning                                                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **belief**    | The probability (0–1) that a natural-language statement holds of the current state. Jev calls this question type `noul`. |
| **state**     | The value a flow's beliefs are evaluated against. Always the flow's arguments.                                           |
| **flow**      | A function whose body is a guard list.                                                                                   |
| **guard**     | `condition [@ threshold] -> action`.                                                                                     |
| **action**    | Plain TypeScript: an expression or a block. May be a nested guard list (`guards { … }`).                                 |
| **preflight** | The single batched evaluation issued at the top of a flow.                                                               |
| **island**    | A region of raw TypeScript embedded in bel.                                                                              |
| **label**     | A rubric level name such as `low` / `high`.                                                                              |

## 5. Types

| Type            | Values               | Notes                                                                            |
| --------------- | -------------------- | -------------------------------------------------------------------------------- |
| `belief`        | real 0–1             | Not a number. Arithmetic is a compile error. Composition is `&`, `\|`, `~` only. |
| `score<N>`      | integer 0–N-1        | The **argmax rubric level**. Ordered.                                            |
| `choice`        | string literal union | The most probable option.                                                        |
| everything else | TypeScript           | passed through                                                                   |

### 5.1 Score is an ordinal, not the raw model output

Jev answers a `score` question with a **float** (`{ "score": 1.97, "confidence": 0.87, "probabilities": {...} }`).
bel deliberately discards the float as the value and uses the argmax level:

```
urgency = score "how urgent is this?" in low | medium | high | human
urgency >= high        # true when level 2 has the largest probability mass
```

Rationale: `score<N>` is documented as an ordered integer, and `>=` must mean
what a reader expects. In the probe above the argmax is `high` (0.88), even
though the float mean 1.97 sits just below 2. The float is not exposed as a bel
value in v0 (see "Known ceilings").

### 5.2 Confidence is defined by the language for `noul`

Jev returns `{ type: "noul", noul: 0.86 }` — a probability and nothing else.
bel defines:

```
confidence(p) = |p - 0.5| * 2      # 0.5 -> 0, 0 or 1 -> 1
```

For `score` and `choice`, confidence is the probability of the argmax
(`probabilities[argmax]`).

## 6. Modules and declarations

- File extension: `.bel`. One file is one ES module. `import` / `export`
  behave as in TypeScript.
- Top level allows `import`, `type` / `interface`, `export flow`, `flow`,
  `route` (parsed, rejected in v0), `mock beliefs`, `test`, `test.snapshot`.
- **A flow is exported only when prefixed with `export`.** A bare `flow` is
  module-private.
- **Top-level belief bindings do not exist.** A belief is a probability about a
  state, and there is no state outside a flow. All `let` bindings live inside a
  flow, so the state is always unambiguously that flow's arguments.

## 7. Syntax

### 7.1 Lexical

- Identifiers and labels are ASCII: `[A-Za-z_][A-Za-z0-9_]*`. Natural language
  appears only inside string literals — this is what the model reads.

  ```
  let urgency = score "how urgent is this?" in low | medium | high | human
  ```

- A guard list is **indentation delimited**: one level is exactly two spaces or
  exactly one tab. Mixing them within a flow is a compile error.
- Strings: `"…"` with `\\` and `\"` escapes.

### 7.2 Flows and bindings

```
[export] flow <name>(<params>): <ReturnType>
  <guard-list>
```

- The return type is **required**. The emitted function is `async` and its
  TypeScript return type is `Promise<ReturnType>`.
- Before the guard list a flow may bind beliefs, scores and choices:

```
flow support(t: Ticket): Action
  let angry = "the user is angry"
  let urgency = score "how urgent is this?" in low | medium | high | human

  angry & (urgency >= high) -> escalate(t)
  _ -> reply("could you tell me more?")
```

- `score` / `choice` may appear **only** as the right-hand side of a flow-level
  `let`. They cannot be written inline in a guard, because an unnamed question
  cannot be traced or mocked.

### 7.3 Guards

```
<belief-expr> [@ <number>] -> <action>
_ -> <action>
```

- `@ n` requires `0 <= n <= 1`. Default threshold is `0.5`.
- `_` is the catch-all. It is required unless the declared return type includes
  `undefined` (see §12).
- Nested guard lists are written `-> guards { … }`, which keeps one flow equal
  to one batched evaluation:

```
"the user is angry" ->
  guards {
    urgency >= high -> escalate(t)
    _ -> refund(t)
  }
```

### 7.4 Belief expressions

```
<belief> ::= <belief> "&" <belief>        // composition (see §8.2)
           | <belief> "|" <belief>
           | "~" <belief>
           | "(" <belief> ")"
           | <string-literal>              // belief literal
           | <ident>                       // reference to a flow-level binding
           | <ident> (">=" | ">" | "<" | "<=" | "==") (<label> | <integer>)
```

- Precedence: `~` > `&` > `|`.
- **`@ n` is the only threshold for a belief.** A numeric comparison such as
  `"the user is angry" > 0.8` is a syntax error, so a guard has exactly one
  place where its threshold is stated.
- Comparisons against a `score` (`urgency >= high`, `urgency >= 2`) or a
  `choice` (`intent == refund`) yield a deterministic 0/1 belief and compose
  with `&` / `|` / `~`.
- Evaluation does not short-circuit. The preflight has already evaluated every
  operand, and the belief layer has no side effects.

### 7.5 Action islands

- The right-hand side of `->` is raw TypeScript — a single-line expression or a
  `{ … }` block — passed through to the output. `guards { … }` is the one
  reserved form.
- Text is scanned to find the end of an island. The scanner tracks string,
  template literal, comment and regular expression state, so braces inside
  those do not terminate it.
- Flow-level bindings are emitted as `const` declarations before the guard list,
  so island code such as `escalate(t) if urgency >= 2` is valid TypeScript as
  written. A rubric label is **not** emitted as a constant: level comparisons
  inline their literal (an index for a `score`, the option name for a `choice`),
  because a label called `refund` would otherwise shadow an imported `refund`
  for the whole flow body — and an island cannot tell a label read from a
  function call.
- **Only erasable TypeScript is allowed**: no `enum`, no `namespace` with a
  runtime value, no parameter properties, no `declare` fields. The compiler
  rejects them, because the emitted `.ts` is executed by a type-stripping
  runtime (see §9).

### 7.6 Tests

```
mock beliefs
  "the user is angry" => 0.9
  "how urgent is this?" => 2          // integer: rubric level
  "how urgent is this? (raw)" => 1.97 // decimal: raw value (see §11.1)

test "an expired refund explains the policy"
  ticket = expiredTicket()
  action = await support(ticket)
  assert action is Explain("refund window has passed")

test "an uncertain decision goes to a human"
  with confidence_floor 0.6
    assert (await support(ambiguousTicket)) is Escalate(_)

test.snapshot "production behaviour"
  record "cassettes/support.v1.json"
  assert (await support(fakeTicket)) is _
```

A test body is a TypeScript island (§7.5) with two pieces of sugar:

- `name = value` declares a local: it compiles to `const name = value`.
- `assert <expression> is <Pattern>` replaces the assertion library's call
  (§11.3).

## 8. Semantics

### 8.1 Guard evaluation

Guards are evaluated top to bottom; the first guard whose condition meets its
threshold fires, and nothing falls through. If no guard fires and there is no
catch-all, the flow returns `undefined`.

### 8.2 Composition

| Expression | Meaning            | Default implementation            |
| ---------- | ------------------ | --------------------------------- |
| `a & b`    | both hold          | `a * b` (independence assumption) |
| `a \| b`   | at least one holds | `a + b - a*b`                     |
| `~a`       | does not hold      | `1 - a`                           |

`&` assumes the operands are independent, which is the known weak point:
"the user is angry" and "the user is complaining" are correlated, so `a * b`
underestimates the joint probability. The compiler routes composition through
`__bel.composeAnd` / `__bel.composeOr` / `__bel.negate` so the rule lives in one
place, and the runtime can be constructed with
`andStrategy: "mul" | "conjoin"`:

- `mul` — multiply the operands. Default.
- `conjoin` — ask Jev for the conjunction as a single question. It needs the
  operand question texts, which is why an `Evaluation` carries its `text`
  (§10). An operand that is a plain number — a deterministic comparison, or a
  composite that already collapsed — carries no text, so conjoining it falls
  back to `mul`.

`composeAnd` / `composeOr` are variadic, so an n-ary `&` stays one call. A
nested composite collapses to a number, which is why `conjoin` only sees the
texts of the operands at that level.

A deterministic comparison is emitted as `__bel.det(boolean)` — a 0/1 belief
with no question text. Naming it `det` keeps the emitted code honest about
which operands the model actually judged.

### 8.3 Confidence and floors

Confidence follows §5.2. `with confidence_floor n` applies to a block: an
evaluation whose confidence is below `n` is treated as not holding, by zeroing
its value at evaluation time. Consequently `~` of an unconfident belief becomes
true — that inversion is the point of the feature: it makes the "what happens
when the model is unsure" path testable.

### 8.4 Preflight flattening

The compiler statically collects **every** belief, score and choice reachable in
a flow, including inside `guards { … }` blocks, and issues one
`evaluate(questions, state)` at flow entry. Questions that never fire are still
sent. This is what makes guard evaluation O(1) API calls; extra questions cost
input tokens but no latency, because Jev evaluates questions in parallel.

A separate flow called from an action island issues its own preflight. Batches
are never shared across flows, because a shared batch would require leaking the
caller's questions into the callee.

### 8.5 Beliefs inside action islands

A flow-level binding becomes a `const` in the emitted TypeScript: a `belief` and
a `score` become numbers, a `choice` becomes a string, and rubric labels become
integer (or string) constants. Therefore a comparison inside an island is an
ordinary TypeScript comparison.

It is **not** a guard: no `@` threshold, no confidence floor, no trace entry,
and no static collection into the preflight. This is the documented exception
to principle 1 (principle 5 in §3). Branching that should be probabilistic belongs in the
guard list.

## 9. Compilation model

`bel build` emits `<name>.bel.ts` next to the source (overridable with
`--out-dir`). Test and mock declarations are stripped; the invariant is that
**their presence or absence does not change one byte of the production
output**.

Source:

```
export flow support(t: Ticket): Action
  let urgency = score "how urgent is this?" in low | medium | high | human

  urgency >= high -> escalate(t)
  "the user is angry" & "the user asks for a refund" @ 0.7 -> refund(t)
  _ -> reply("could you tell me more?")
```

Output:

```ts
// @generated from bel source. Do not edit.
import { __bel } from "@bel/runtime";

import { escalate, refund, reply } from "./actions.ts";

export async function support(t: Ticket): Promise<Action> {
  const $b = await __bel.evaluate(
    [
      {
        id: "0",
        type: "score",
        text: "how urgent is this?",
        rubric: ["low", "medium", "high", "human"],
      },
      { id: "1", type: "noul", text: "the user is angry" },
      { id: "2", type: "noul", text: "the user asks for a refund" },
    ],
    t,
  );
  if (__bel.det(__bel.number($b[0]) >= 2) >= 0.5) {
    __bel.mark("support", 0);
    return escalate(t);
  }
  if (__bel.composeAnd($b[1], $b[2]) >= 0.7) {
    __bel.mark("support", 1);
    return refund(t);
  }
  __bel.mark("support", 2);
  return reply("could you tell me more?");
}
```

- Questions are collected in source order — flow-level bindings first, then the
  guards depth first — deduplicated by `(type, text)`.
- The runtime is a module singleton obtained from `@bel/runtime`;
  `configureBel(runtime)` swaps it. Generated production code imports only
  `@bel/runtime`.
- `__bel.mark(flow, index)` records which top-level guard fired, including the
  catch-all, so a trace can tell "the fallback ran" from "nothing ran".
- A binding is emitted as a `const` only when an action island reads its name.
  Everything else is read straight from `$b`, so generated files carry no
  unused declarations.
- A number is read with `__bel.number(evaluation)`, not `.value`: the array an
  `evaluate` call returns is a union of the three question types, so `.value` is
  `string | number` even where the question is statically known to be a belief
  or a score. Type checking the output is what caught this.
- A plain parameter is the state; several parameters become `{ a, b }`. A
  destructured parameter has no name to pass, and is an error.
- `bel test` emits `<name>.bel.test.ts` and runs it with vitest.

### 9.1 Execution

The emitted TypeScript is executed directly by a runtime that strips types
(Node 24+, Deno, Bun). No JavaScript artifact is produced for user code.
`@bel/runtime` and `@bel/testkit` are the exception: they are published
JavaScript plus `.d.ts`, because Node refuses to strip types inside
`node_modules`.

Consequently imports carry the `.ts` extension and the workspace sets
`allowImportingTsExtensions` with `noEmit`; type checking is a separate pass.

## 10. Runtime API

```ts
type Question =
  | { id: string; type: "noul"; text: string }
  | { id: string; type: "score"; text: string; rubric: string[] }
  | { id: string; type: "choice"; text: string; rubric: string[] };

type Evaluation =
  | { id: string; type: "noul"; text: string; value: number; confidence: number }
  | {
      id: string;
      type: "score";
      text: string;
      value: number;
      confidence: number;
      raw: number;
      probs: number[];
    }
  | {
      id: string;
      type: "choice";
      text: string;
      value: string;
      confidence: number;
      probs: Record<string, number>;
    };

/** A transport: where the probabilities come from. */
interface BelRuntime {
  evaluate(questions: Question[], state: unknown): Promise<Evaluation[]>;
}

/** The surface the generated code calls. */
declare const __bel: {
  evaluate(questions: Question[], state: unknown): Promise<Evaluation[]>;
  /** The numeric reading of an evaluation; a choice has none and throws. */
  number(operand: number | Evaluation): number;
  composeAnd(...operands: (number | Evaluation)[]): number;
  composeOr(...operands: (number | Evaluation)[]): number;
  negate(operand: number | Evaluation): number;
  /** A deterministic comparison: 0 or 1. */
  det(holds: boolean): number;
  mark(flow: string, guard: number): void;
  floor: number;
};

function configureBel(
  config: BelRuntime | { runtime: BelRuntime; floor?: number; traceLimit?: number },
): void;
function trace(): Trace[];
```

A runtime implements one method. Composition, the confidence floor, `det`, the
trace buffer and `mark` live on `__bel` and are identical for every transport,
which is what keeps a mock and a cassette to a single function each.

The live adapter posts to `POST https://api.typesafe.ai/v1/systemone`
(`model: "jev-latest"`), retrying 429 and 529 three times with backoff, and
reads `TYPESAFE_API_KEY`, `BEL_MODEL`, `BEL_API_URL` when the caller passes
nothing. The runtime is built on first use, so importing the module without a
key is fine — only evaluating a belief needs one.

`model: "jev-latest"` is an alias; the response reports the resolved build
(`jev-1.13.0`). Cassettes therefore record the resolved version, and recording
pins `BEL_MODEL` to it, so a model upgrade shows up as a diff rather than as a
silently changed replay.

## 11. Testing

### 11.1 Mock beliefs

`mock beliefs` is a **file-scoped** top-level declaration. Its keys are the
`text` of a question, so the type of a mocked value follows from the bel source:

| Question type | Mock value                                                             |
| ------------- | ---------------------------------------------------------------------- |
| `noul`        | probability, `0.9`                                                     |
| `score`       | integer rubric level, `2` (`confidence = 1.0`), or a decimal raw value |
| `choice`      | option name, `"refund"`                                                |

A decimal mock value `1.97` means the raw score: the level is `round(1.97) = 2`
and confidence is `1 - |1.97 - 2| = 0.97`. An object form
`{ score, level, confidence }` overrides every field.

Because mock tables and flows are compiled together, **coverage is checked at
compile time**: a question that a flow asks but the table does not list is an
error, and so is a table entry that no flow asks.

A `test` with neither `mock beliefs` nor a cassette is a compile error — a test
whose answer comes from the live model is not a test.

### 11.2 Cassettes

`test.snapshot` records live responses to a JSON cassette and replays them.
The entry key is a hash of canonical JSON (sorted keys) of
`{ model, questions, state }`. Replay is the default; recording happens only
when `BEL_RECORD=1` is set. A replay miss is a test failure.

State must be deterministic: `Date.now()`, random ids and other varying values
change the key and defeat the cassette.

`bel test` compiles each `<name>.bel.test.ts` next to its source and runs the
generated files with Vitest, reached through Vite+ (`vite-plus/test`), which is
what a Vite+ project already has.

### 11.3 Assertions

```
assert <expr> is <Name>(<arg>, …)
```

An **action is a plain object `{ type: string, args: unknown[] }`**. The
assertion checks the `type` discriminant and then each argument that is not
`_`:

```ts
const $actual = action;
expect($actual?.type).toBe("Explain");
expect($actual?.args).toHaveLength(1);
expect($actual?.args?.[0]).toEqual("refund window has passed");
```

- `_` in an argument position skips that argument's value, **not** its place:
  `Escalate(_)` still requires one argument.
- `is _` is a whole-value wildcard: it only asserts the result is not
  `undefined`.
- The arity is always checked, so a pattern cannot silently accept a different
  shape.

## 12. Diagnostics

Strict by default: **every diagnostic is an error** and there is no
`--strict` / `--no-strict` flag. Severity exists in the shape of a diagnostic
for future use.

| Code                    | Trigger                                                    |
| ----------------------- | ---------------------------------------------------------- |
| `missing-fallback`      | return type does not include `undefined`, but no `_` guard |
| `unreachable-guard`     | a guard after `_`, or after a constant-true belief         |
| `unknown-belief`        | reference to a binding that does not exist                 |
| `bad-threshold`         | `@ n` outside 0–1                                          |
| `mock-missing-question` | a flow asks a question the mock table does not list        |
| `mock-unused-entry`     | a mock table entry no flow asks                            |
| `test-without-answers`  | a `test` with neither mocks nor a cassette                 |
| `route-not-implemented` | `route` used in v0                                         |
| `non-erasable-syntax`   | `enum` / `namespace` / parameter property in an island     |
| `indent-mixed`          | spaces and tabs mixed within a flow                        |

Diagnostics carry a span mapped from the parser position to line and column in
the `.bel` file.

## 13. Non-goals

- Re-evaluating beliefs inside a loop; v0 re-evaluates only through an explicit
  flow call.
- Being a superset of TypeScript files. bel changes one semantic, so it is a
  separate language with islands.
- Probability calibration. That is the model's responsibility; bel only refuses
  to hide the numbers.
- **`belief` is not a security boundary.** Authentication, authorization and
  billing must not be decided by a belief. Those are deterministic code; bel
  only chooses which way to lean.
- `route` and HTTP backends (RFC 0002).

## 14. Alternatives and decisions

| Decision                 | Chosen                           | Rejected                                     | Why                                                                                                                                                      |
| ------------------------ | -------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Value of `score<N>`      | argmax level                     | raw float; cumulative probability            | keeps `score<N>` an ordered integer and `>=` intuitive; the float distorts the type and the cumulative form makes thresholds unreadable                  |
| `noul` confidence        | `\|p-0.5\|*2`                    | `null`; constant `1`                         | Jev returns no confidence; a constant makes the floor a no-op and the tests dishonest; `null` pollutes every consumer of `Trace`                         |
| Composition of `&`       | `a*b`, pluggable                 | always re-ask Jev as one question            | preserves the single batched call; the accuracy question is settled by measurement, not by prose                                                         |
| Threshold syntax         | `@ n` only                       | allow `belief > n` too                       | one way to state a threshold keeps `takenGuard` traceable; comparisons inside a belief expression collapse to 0/1 and compose meaninglessly              |
| Nested guards            | `-> guards { … }`                | indentation-based nesting; separate flows    | keeps one flow = one preflight; a separate flow costs another round trip                                                                                 |
| Belief bindings          | flow-level `let` only            | top-level `let`                              | a belief is about a state, and outside a flow there is none                                                                                              |
| Mock key                 | question `text`                  | per-test tables; runtime strings             | type follows from the source; one table per file matches how questions are collected                                                                     |
| Mock coverage            | compile error                    | runtime failure                              | the questions are statically known, so there is no reason to defer                                                                                       |
| Answer source in tests   | required (mock or cassette)      | live by default                              | a test that calls the model is not a test                                                                                                                |
| Action shape for `is`    | `{ type, args[] }`               | single `value`; field names from the TS type | one rule for any arity, five lines of lowering, no TypeScript type parsing                                                                               |
| Return type              | required annotation              | inferred by `tsc`                            | keeps `missing-fallback` decidable in every flow                                                                                                         |
| Rubric labels in islands | comparisons inline their literal | emit labels as named constants               | a label called `refund` would otherwise shadow an imported `refund` for the whole flow body, and an island cannot tell a label read from a function call |
| Diagnostics              | all errors, no flag              | warnings; `--strict`                         | a lenient path kept around is a lenient path used                                                                                                        |
| Output                   | `<name>.bel.ts`, run directly    | emit JavaScript                              | Node 24 / Deno / Bun strip types; a second artifact buys nothing for user code                                                                           |
| Labels                   | English ASCII                    | Unicode labels                               | natural language belongs in the string, not in the lexer                                                                                                 |
| Composition runtime      | module singleton                 | parameter threading                          | keeps generated signatures clean; one injection point for tests                                                                                          |
| `&` strategy             | compiler option                  | runtime option                               | `conjoin` changes the question set, which preflight exists to make static, and `composeAnd` cannot await a second model call                             |

## 15. Resolved open questions (draft v0 §10)

1. **Is `a*b` right for `&`?** Ship `a*b` behind `composeAnd`, measure the
   `conjoin` strategy against it with cassettes, then decide. Not decidable on
   paper.
2. **Must the catch-all `_` be required?** Required unless the return type
   allows `undefined`. With strict diagnostics an omitted fallback is an error,
   never a silent `undefined`.
3. **Are implicit rubric ordinals safe?** Yes, because labels are explicit
   ASCII identifiers rather than ordinal-looking words, and the value is the
   argmax level. No `低=1 | 中=2` syntax is needed.
4. **How far should return-type inference go?** None. The return type is
   required.

## 16. Known ceilings

Deliberate limitations with a named upgrade path.

| Ceiling                               | Consequence                                                                       | Upgrade                                                      |
| ------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Global trace ring buffer              | traces from concurrent requests interleave                                        | scope traces per request (AsyncLocalStorage)                 |
| `&` independence                      | correlated beliefs are underestimated                                             | `andStrategy: "conjoin"`                                     |
| `jev-latest` alias                    | replay keeps working across a model upgrade                                       | cassettes record the resolved version; pin it when recording |
| Confidence floor is a runtime field   | may leak across concurrent tests                                                  | pass the floor as a flow parameter                           |
| No accessors                          | `.score` (raw float) and `.dist` (distribution) are unreachable                   | emit companion constants                                     |
| Erasable syntax only                  | `enum` / `namespace` cannot be used in islands                                    | emit JavaScript for those projects                           |
| Regex detection in islands            | a `/` in an unusual position is read as a regex, not division                     | parse the island with oxc instead of scanning it             |
| One batch per flow                    | a flow called in a loop re-evaluates                                              | hoist the call or pass resolved values                       |
| Mock keys are question text           | two questions with the same words but different types collide                     | key the table by `(type, text)`                              |
| Erasable detection is textual         | an `enum` mid-line, or a `private` in a constructor comment, is missed or misread | parse the island with oxc instead of scanning it             |
| Which flows a test reaches is textual | a flow named only in a string is not followed                                     | follow calls through a real module graph                     |
